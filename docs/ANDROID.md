# Android: native layer and emulator testing

Unit tests can't catch problems in the native Android layer: the media session, the notification, Bluetooth/media buttons, R8 and resource shrinking. Verify anything touching `android/`, Gradle/AGP/Kotlin versions, or `packages/voidweaver_player/` (or its Media3 version) in the emulator with a **release** build, as described below. How the session and system controls work is described in [PLAYBACK.md](PLAYBACK.md#bluetooth-and-system-controls).

## Environment

- Gradle needs a JDK. Android Studio ships one; on macOS: `export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"`.
- The Android SDK is expected at `~/Library/Android/sdk` (the scripts honor `ANDROID_SDK_ROOT`). `adb`, `emulator`, and `apkanalyzer`/`sdkmanager`/`avdmanager` live under `platform-tools/`, `emulator/` and `cmdline-tools/*/bin/`; `aapt2` lives under `build-tools/<version>/`.
- The scripts and the coordinates below assume a 1080x2400 screen, e.g. a Pixel 8 AVD (Android 16, arm64) or the `pixel_6` profile (same screen).

## Running the app in the emulator

```bash
SDK=~/Library/Android/sdk; ADB=$SDK/platform-tools/adb
$SDK/emulator/emulator -avd <your AVD> -no-snapshot -no-boot-anim &   # run in background
$ADB wait-for-device; until [ "$($ADB shell getprop sys.boot_completed | tr -d '\r')" = 1 ]; do sleep 2; done

tool/build_release_apk.sh   # arm64 only, so the AVD must be arm64 too
$ADB install -r build/app/outputs/flutter-apk/app-release.apk   # -r keeps the login
$ADB shell am start -n red.ochsenbein.voidweaver/.MainActivity      # `monkey` fails on Play Store images
```

**Logging in:** the app only accepts `https://` URLs. Use your own server, or `tool/emulator_check.sh --fake-server` (below), which needs none. Never commit credentials. On a fresh install:

- tap the Server URL field at (540, 1186) in device pixels (1080x2400);
- type with `adb shell input text '...'`;
- move to the next field with `input keyevent 61` (Tab), not taps, because the keyboard shifts the layout;
- after the password, `input keyevent 66` (Enter) submits the form, like the Connect button.

Don't send Back (`keyevent 4`) when the keyboard is already hidden, because that closes the app. `adb shell pm clear red.ochsenbein.voidweaver` resets to the login screen.

After login, tapping the first album card at (400, 550) starts playback. Tapping the seek bar at (1035, 1903) jumps to the last few seconds of the track, which is how to test the gapless move to the next track and the end of the playlist.

**Offline:** `$ADB shell svc wifi disable; $ADB shell svc data disable` (`enable` to undo). The next 3 tracks are downloaded, so skip past them with `MEDIA_NEXT` to reach a track that has to stream and fails to load. Playback should stop there, paused, with the session still active; with the network back, Play loads it again.

**Network events in the emulator:** `NetworkMonitor` (and with it the resume after a network failure, and restarting downloads, see [PLAYBACK.md](PLAYBACK.md#when-the-network-comes-back)) only reacts to a *validated* default network. In the AVD no network passes Android's internet check, so it never fires, whatever you toggle (`dumpsys connectivity`: no `VALIDATED` in the network's capabilities; the default network is mobile data, so toggling Wi-Fi doesn't even change it). To test it, turn the check off with `$ADB shell settings put global captive_portal_mode 0`, then `svc data disable` / `enable`: the network comes back validated and the app gets the event. Undo with `$ADB shell settings delete global captive_portal_mode`. The same holds on a phone: a network without internet access (e.g. Wi-Fi with only the home server) never counts as back.

**Screenshots:** `$ADB exec-out screencap -p > x.png`. They're 1080x2400; if you view them scaled down, scale the coordinates back up before tapping.

## Checking the media session, notification and Bluetooth controls

This is the part most likely to break silently.

`tool/check_release_apk.sh` checks the release APK itself, without a device: Media3's notification icons are there and not shrinker placeholders, the manifest declares `PlaybackService` and the media button receiver, the [launcher shortcut](#launcher-shortcut) and its icon are there, so are the [home screen widget](#home-screen-widget)'s provider, layouts and icons, their classes survived R8, and the native code is for arm64 only (also the plugins' libraries, which `android/app/build.gradle.kts` limits to the ABIs of `--target-platform`). CI runs it after the release build; `make check-apk` builds and runs it. It catches the shrinker failure described under [Known pitfalls](#known-pitfalls), but not a session that's broken at runtime.

`tool/emulator_check.sh` runs the checks below (session, notification, media keys, gapless move to the next track, playing again after Android stopped the idle service, playback resumption, app errors in logcat) against a booted emulator with the app logged in, and exits non-zero on a failure. It waits for screens and taps elements through `uiautomator` rather than fixed delays, stops early when the app, the login or the first playback fails, and saves a screenshot, the UI hierarchy and logcat to `build/emulator-check/diagnostics/`. `make check-emulator` builds the release APK first; the APK is arm64 only, so the script stops before installing on an emulator without arm64 (with `--build`, before the build); `--apk <file>` installs another build, e.g. a known-good one to compare. Run it after every change to playback, login, the native layer or the toolchain. `make check-emulator-fake` (`--fake-server --build`) needs no server or credentials: it builds a release APK that trusts the tests' fake Subsonic server, runs that server on the host, clears the app's data and logs in to it. CI doesn't run it (it failed at the login step in the runner's emulator), so run it locally; `tool/release.sh` runs it before a release when an emulator is running, see [RELEASING.md](RELEASING.md). The trusting APK goes to `build/emulator-check/`; never install it anywhere else.

The manual steps below are for investigating when it fails, and for what it doesn't cover (offline, untrusted controllers).

```bash
$ADB shell dumpsys media_session | grep -A12 "package=red.ochsenbein.voidweaver" | grep -E "active=|state=PlaybackState|description="
$ADB shell input keyevent KEYCODE_MEDIA_PAUSE     # also MEDIA_PLAY, MEDIA_NEXT, MEDIA_PREVIOUS,
$ADB shell input keyevent KEYCODE_MEDIA_PLAY_PAUSE # MEDIA_PLAY_PAUSE (= headset button)
$ADB shell cmd statusbar expand-notifications      # then screenshot; `collapse` to close
```

Media key events go through MediaSessionService to the active session, the same path Bluetooth/AVRCP buttons use.

- **Healthy:** `active=true`, the state follows the keys (`PLAYING(3)` / `PAUSED(2)`), and the shade shows the media player with artwork.
- **Broken:** `active=false` with `state=NONE(0)` while audio plays.

**Playback resumption** (Play after the process died): start playback with the app's Play button (Android only sends media keys to a session that has played audio), pause, swipe the app away in Recents (`input keyevent KEYCODE_APP_SWITCH`, then `input swipe 540 1300 540 150 300`), go Home and run `$ADB shell am kill red.ochsenbein.voidweaver` until `pidof` prints nothing. Don't use `am force-stop`: it disables the app's receivers. Then `input keyevent KEYCODE_MEDIA_PLAY` should start a new process that plays the saved track within seconds, with a single session in `dumpsys media_session`: the `resume` session, which the app's player took over. `Media button session is` must name it; if it says `null`, only Play reaches the app (`MediaButtonReceiver: Ignore key event that is not a play command` in logcat), so check that `MEDIA_PAUSE` and `MEDIA_NEXT` still work afterwards.

**System UI's resumption controls:** after a play, logcat should show `MediaResumeListener: Testing if we can connect to …PlaybackService` without a following `Cannot resume with`, and `dumpsys activity service com.android.systemui | grep resumeAction` should show a `resumeAction` for the app. Paused for more than 10 minutes, the player in the shade then turns into resumption controls instead of disappearing.

When it's broken, check `$ADB logcat -d --pid=$($ADB shell pidof red.ochsenbein.voidweaver) | grep -E " [EW] |Exception"`.

**Compare against a known-good build.** If behavior differs, build the previous commit too and install each in turn. Diff the merged manifests (`build/app/intermediates/merged_manifest/release/...`) and the resources (`aapt2 dump resources <apk>`).

## Launcher shortcut

Long-pressing the app icon offers **Play random songs** (short label "Random"; it can be dragged to the home screen). It starts random songs as the shuffle button in the app bar does, replacing what was playing, and opens the app.

- **Static shortcut.** `res/xml/shortcuts.xml`, referenced by the `android.app.shortcuts` meta-data of `MainActivity`, so it exists from install without running any code. Its intent has the action `red.ochsenbein.voidweaver.action.PLAY_RANDOM` and names `MainActivity`. Keep the shortcut id (`random`) and the action: a shortcut pinned to the home screen refers to them. The icon is an adaptive icon in the launcher icon's colors (black on white), with a `monochrome` layer for themed icons, and a plain vector for Android 7.1.
- **`MainActivity` notes the tap.** Launchers start a static shortcut with `NEW_TASK | CLEAR_TASK` (`flg=0x1000c000` in `dumpsys shortcut`), so a tap recreates the activity and arrives in `onCreate()`; `onNewIntent()` covers an intent without `CLEAR_TASK` while the activity is on top. Either sets a static flag, which outlives the activity like the engine does. The task keeps the shortcut's intent as its base intent, so reopening the app from Recents, also after the process died, hands it in again: a launch with `FLAG_ACTIVITY_LAUNCHED_FROM_HISTORY` or saved state is ignored, or the app would start random again on every return from Recents.
- **Dart asks.** `MainActivity.configureFlutterEngine()` answers `takeRandomRequest` on the channel `voidweaver/shortcuts` with the flag, clearing it (`getAndSet(false)`), so a tap is taken once. `AppRouter` asks once the app is initialized and whenever it's resumed: the activity resumes after `onCreate()` and `onNewIntent()`, so a tap is never left waiting, also when the engine was already running without an activity. If nobody is logged in, the tap is dropped (`Random shortcut ignored: not logged in` in the log), not kept for after the login. The handler holds no activity; each activity that attaches to the cached engine sets it again. An engine started for playback resumption has none until an activity attaches; Dart takes the missing handler for "no tap".
- **Any app can send the action.** `MainActivity` is exported (it's the launcher activity), so another app can start it with `PLAY_RANDOM` too. That's accepted: all it does is what the shuffle button does, starting random songs from the user's own server; it returns nothing and changes no setting.

To check it by hand (the log tag is `VoidweaverShortcut`, Dart's lines are under `flutter`):

```bash
$ADB shell dumpsys shortcut | grep -A12 "id=random"   # registered, with its intent and flags
# the path of a launcher tap (onCreate); without -f while the app is in front: onNewIntent
$ADB shell am start -a red.ochsenbein.voidweaver.action.PLAY_RANDOM -f 0x1000c000 -n red.ochsenbein.voidweaver/.MainActivity
$ADB logcat -d -s VoidweaverShortcut:I flutter:I | grep -iE "shortcut|random songs"
```

In the Pixel launcher, open the app drawer (`input swipe 540 2000 540 600 300`) and long-press the icon (`input swipe <x> <y> <x> <y> 1200`) for the popup. Check at least: a tap with the process gone, with the app in front, with an album playing in the background, and after Back; reopening from Recents afterwards must log `Redelivered shortcut ignored` and not start random.

## Home screen widget

The plugin's `PlayerWidget` (an `AppWidgetProvider`, declared in the plugin's manifest; label "Player") shows the current track with its cover, Play/Pause, Next, and a shuffle button that starts random songs. Below 120 dp high it's one row (cover, title and artist, Play, Next, Random); from 120 dp it adds the album. On Android 12+ the launcher picks the layout for the size (`RemoteViews` with a layout per size) and the colors follow the wallpaper; before that, `onAppWidgetOptionsChanged()` picks it and the colors are black and white.

- **What it shows.** The player of the session that played last: a `Player.Listener` on the app's `SessionPlayer` and on the resumption stand-in (`ResumePlayer`) redraws it on every change, and only while that player is the session's (a player that claimed the stand-in's session shows once `PlaybackService.handOver()` gave it the session). Without a player (the app isn't running, or nothing is loaded yet) it shows the track saved for playback resumption (`RecentItem`), paused; the stand-in shows it as playing once Play was pressed. After a logout `RecentItem` is cleared before the player is released, so it shows "Nothing playing" with only the Random button. Random is kept there because that's also how it looks right after a login; while logged out, a tap opens the login screen and the request is dropped (see [Launcher shortcut](#launcher-shortcut)).
- **The cover** comes from the session's bitmap loader, so it's the notification's (and works offline through the audio cache, see [CACHING.md](CACHING.md#audio-files-media3-cache)), scaled to 320 px for the launcher. It stays across tracks with the same cover (`ArtworkLoader.key()`). Covers are told apart by a SHA-256 of that key (`RecentItem.coverKey()`), since for artwork without a cache key it's the URL, with the credentials.
- **The recent track's cover** is the one the widget showed for it: `RecentItem.saveCover()` keeps the scaled bitmap in `noBackupFilesDir` (a JPEG, or a PNG for a cover with transparency, `RecentItem.formatFor()`), with the hashed key and the track's id in `RecentItem`'s prefs, so it shows after the app was closed, after a reboot, and while the stand-in waits for the app. The file and its prefs entries are written and read on a thread of their own, the entries only once the file is complete; a logout (`RecentItem.clear()`) deletes them, also a write still in progress. Another track's cover is never shown: the entries name the track.
- **A cover that failed for the network** (no connection, no route, a timeout: `CoverRetry.isNetworkFailure()`) is loaded again when a network comes back, at most 3 times per cover (`CoverRetry`, which asks the widget whether the cover is still the one missing). It waits with a `NetworkMonitor.Callback` of its own, which is registered only while it waits; the network that was there when the load failed doesn't count. The retry goes through the `ArtworkLoader` itself: the session's `CacheBitmapLoader` keeps the last load also when it failed, and would hand out the failure again. A cover the server refused (an HTTP error, a Subsonic error document) isn't retried: the request would fail the same way, and failed logins add up (see [Rejected credentials](DEVELOPMENT.md#rejected-credentials)). So a retry sends at most 3 more requests per cover, only after requests that didn't reach the server, and a rejected login (an error document) ends it at once; the widget doesn't see Dart's rejected-credentials flag.
- **Play/Pause is a media button** to `PlaybackService`, built by Media3's `PlaybackPendingIntentBuilder`, the path the notification's buttons take. Paused, it's a foreground-service start: a widget tap may start a foreground service from the background (`Background started FGS: Allowed ... code:START_ACTIVITY_FLAG` in logcat), so Play works after Android stopped the service, and after the process died (the stand-in starts the app and resumes, as for a Bluetooth Play).
- **Next works while playing**; paused, it's dimmed. A skip starts playback (see [PLAYBACK.md](PLAYBACK.md#skips)), which needs `PlaybackService` in the foreground, and Android doesn't let a widget start it in the background except for Play: while paused, the service may be stopped or out of the foreground, and the skip's playback would run without a foreground service (`BackgroundServiceStartNotAllowedException` from `ensureStarted()`), which Android freezes. Bluetooth buttons don't hit this, as Android lets the app start it for a media button. It's a broadcast to `PlayerWidget`, which calls `seekToNext()` on the `SessionPlayer`, so it reaches Dart like any controller's; as a media button to the service, a plain start would be refused while it's stopped (`Background start not allowed ... startFg?=false`). It's also disabled when there's no next track, and without the app's player.
- **Random** opens `MainActivity` with the shortcut's `PLAY_RANDOM` intent and the launcher's flags (`NEW_TASK | CLEAR_TASK`, logged as `flags 0x1000c000`), so it behaves exactly like the shortcut, see [Launcher shortcut](#launcher-shortcut). `PlayerWidget.ACTION_PLAY_RANDOM` is the one constant; `MainActivity` uses it.
- **A new process redraws it.** The launcher keeps the last views, also after the process died, and those may show a playing track. `PlaybackService.onCreate()` (also when Android restarts it after a crash), the plugin and a Next tap (whose broadcast starts the process) draw it once per process, showing the recent track paused. Until then, a stale Pause is a Play/Pause media button: if Android restarts the service, it reaches the stand-in and starts playback; if the process is gone for good, the plain service start is refused and nothing happens.
- **The receiver isn't exported.** Android delivers the widget updates to it anyway (also at boot: `Start proc ... for broadcast {.../.player.PlayerWidget}`), and its own buttons use explicit PendingIntents. `am force-stop` cancels the app's PendingIntents, so the widget's buttons do nothing until the app runs again and redraws it.

To check it by hand (log tags `VoidweaverWidget` and `VoidweaverShortcut`): long-press the home screen, Widgets, search "voidweaver", tap the preview and Add. Then check: the track, cover and buttons follow the app (Play, Next, Pause, a skip from the notification); Next is dimmed on the last track and while paused; Random starts random songs and opens the app; resizing from one row to two switches the layout; after a logout it shows "Nothing playing"; Play works with the service stopped (pause, `KEYCODE_MEDIA_STOP`, `am make-uid-idle red.ochsenbein.voidweaver`, wait until `dumpsys activity services red.ochsenbein.voidweaver` lists no `ServiceRecord`), and Next right after it; `am crash red.ochsenbein.voidweaver` while playing redraws it paused once Android restarted the service; Play after the process died resumes the recent track; the recent track keeps its cover after `am kill red.ochsenbein.voidweaver` (paused, in the background) and after a reboot, and loses it with a logout; a cover whose load timed out (a server that stalls `getCoverArt`; covers are downloaded ahead with the tracks, so going offline alone rarely leaves one missing) loads once a validated network is back (`Network back: loading the cover again` in logcat). That needs a network Android validates: when `dumpsys connectivity` shows no `IS_VALIDATED` for any network, as on an emulator whose connectivity check fails, neither this retry nor Dart's network events fire.

## Known pitfalls

- Plugins that load resources by name at runtime (`getIdentifier`) need keep rules, because the resource shrinker can't see those references. `audio_service` did, and AGP 9's optimized shrinking removed its notification icons, which killed the notification, lock screen player and Bluetooth controls. Media3, which replaced it, references its resources normally.
- System controls (notification, lock screen, Bluetooth/media buttons) come from the plugin's Media3 media session. `SessionPlayer` forwards every command to Dart and shows a player that's idle after a load error as paused; only `stop()` ends the notification. `MainActivity` caches its `FlutterEngine` so Dart runs without the activity. See [PLAYBACK.md](PLAYBACK.md#bluetooth-and-system-controls).
- The sessions outlive `PlaybackService` (they belong to the players), and Media3 doesn't detach them when the service is destroyed, so `PlaybackService.onDestroy()` removes them. A stale notification manager otherwise stops the next instance with its own start intents (`Terminating service that was started by a stale start intent`), and playback runs without a foreground service or notification. `tool/emulator_check.sh` checks it (about two minutes of it is waiting for Android to stop the service). By hand: pause, send `KEYCODE_MEDIA_STOP`, go Home, `$ADB shell am make-uid-idle red.ochsenbein.voidweaver` and wait until `dumpsys activity services red.ochsenbein.voidweaver` lists no `ServiceRecord` (`am_stop_idle_service` in `logcat -b events`, about a minute), then play from the app and go Home: the service must be `isForeground=true` with the notification, still playing after a minute. See [PLAYBACK.md](PLAYBACK.md#bluetooth-and-system-controls).
- The player is the local plugin `packages/voidweaver_player` (Media3 ExoPlayer). ReplayGain is a gain per queue item, applied to the samples by `GainAudioProcessor`, not the player volume; see [PLAYBACK.md](PLAYBACK.md#replaygain-per-track). It relies on Media3 flushing audio processors with `StreamMetadata` at item boundaries (Media3 1.11), so after a Media3 upgrade check `adb logcat -s VoidweaverGain` across a gapless transition.
- The system UI (notification, media keys) is a *trusted* controller; launcher widgets and other third-party apps are not, and Media3 limits untrusted controllers to read access unless the session grants more (`PlayerSession.Callback`). Testing with the notification alone won't catch that. To test like a widget, use a small app that's an enabled notification listener (`adb shell cmd notification allow_listener <component>`) and sends `MediaController.getTransportControls()` commands.
- Audio focus is handled by ExoPlayer in the plugin. Don't request it in `MainActivity` or elsewhere, because that registers a competing listener (see the comment there and [PLAYBACK.md](PLAYBACK.md#audio-focus)).
- The app has no Kotlin code (`MainActivity` is Java, like the plugin) and applies no Kotlin Gradle plugin: it uses AGP's built-in Kotlin (`android.builtInKotlin=true` in `gradle.properties`), which the Dart packages' Kotlin plugins (share_plus, package_info_plus, shared_preferences) support. With `=false`, Flutter warns that the Kotlin version of those plugins "will soon be dropped" and that the option is deprecated. Don't delete the line: the Flutter tool adds `=false` back when the flag is absent (it leaves any value that's set). `android.newDsl=false` is the Flutter migrator's and is untouched.
- Android Lint runs on the player plugin in CI (`make lint-android`, `:voidweaver_player:lintDebug`); errors fail the job. Three checks are turned off in the plugin's `build.gradle.kts`: `UnsafeOptInUsageError` (every use of Media3's `@UnstableApi` classes would be reported) and `GradleDependency` / `NewerVersionAvailable` (newer versions are Dependabot's job, and they'd make the output depend on the date). The warnings that remain are known and meant: `InlinedApi` for `IMPORTANCE_CACHED` in `ProcessHistory` (a constant the compiler inlines, only read on Android 11+), and `ExportedService` for `PlaybackService`, which media controllers must be able to bind.
- When upgrading dependencies, bump the Dart packages and the Android toolchain (AGP/Gradle/Kotlin) in separate steps so regressions can be bisected.
